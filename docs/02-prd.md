# PRD:多智能体 Vibe Coding 平台(Atoms 功能对标)

- 版本:v1.0
- 状态:待评审
- 依据:`docs/01-atoms-core-features.md`(基于 help.atoms.dev 全量 62 篇官方文档的逆向分析)
- 代号:本文档中用 **Forge** 指代我们要做的产品

---

## 1. 背景与目标

### 1.1 我们要解决什么问题

传统"AI 写代码"工具的交付止步于代码片段,用户仍需自己搭环境、配后端、买域名、做 SEO、拉流量。
Atoms 验证了一条更完整的路径:**把一个想法从自然语言描述,一口气推进到有域名、有后端、有支付、能被搜索到、能投广告的线上产品**。

Forge 的目标是复刻这条完整链路,并在若干 Atoms 已暴露短板的地方做得更好。

### 1.2 产品目标

| 层级 | 目标 |
|---|---|
| 用户价值 | 零编程经验者能在 30 分钟内产出一个可公开访问、带数据持久化的 Web 应用 |
| 差异化 | 用"可解释的智能体协作过程"降低 AI 黑箱焦虑;用"成本可预测"解决 credits 焦虑 |
| 商业 | 订阅(能力与配额)+ 用量后付费(Cloud/AI 消耗)双轨变现 |

### 1.3 非目标(v1 明确不做)

- 原生 iOS/Android 二进制、桌面可执行文件(与 Atoms 一致,移动端走 PWA + 响应式)
- 大型企业级复杂业务系统(定位在快速原型、数据可视化、Web 应用、小游戏)
- 自建 LLM(全部走第三方模型 API)
- 自建 CI/CD 平台(通过 GitHub 集成对接用户既有流程)

## 2. 目标用户与场景

### 2.1 用户画像

| 画像 | 占比预估 | 核心诉求 | 关键功能依赖 |
|---|---|---|---|
| **P1 非技术创造者**(学生、教师、销售、运营) | 45% | 不写代码也能做出能给别人看的东西 | 自然语言对话、可视化编辑、一键发布 |
| **P2 独立开发者 / 副业者** | 30% | 快速验证想法,省掉搭架子的时间 | 代码编辑器、GitHub 同步、源码导出、自定义域名 |
| **P3 小团队(产品+设计+开发)** | 15% | 协作与集中计费 | 团队工作区、角色权限、共享额度、实时协同 |
| **P4 小微商家 / 独立创业者** | 10% | 要能收钱、能被搜到、能拉客 | 支付集成、SEO、GA4 分析、广告投放 |

### 2.2 核心用户故事

- **US-1**(P1)作为一名教师,我想把课件变成网页,这样学生可以在线互动 —— 我只想描述需求,不想看到任何代码
- **US-2**(P2)作为独立开发者,我想让 AI 搭好框架后把代码推到我自己的 GitHub 仓库,继续用我熟悉的方式开发
- **US-3**(P3)作为产品经理,我想邀请设计师和工程师进同一个会话,大家能同时和智能体对话,费用统一走我的套餐
- **US-4**(P4)作为独立商家,我想做一个能用信用卡收款的商品页,并且让它在 Google 上能被搜到
- **US-5**(全体)作为用户,当构建出错时,我希望点一个按钮就能修好,而不是去读堆栈信息
- **US-6**(全体)作为用户,我希望在花钱之前就知道这次操作大概要花多少,以及我的余额还能撑多久

## 3. 功能需求

优先级定义:**P0** = MVP 必须有,缺失则产品不成立;**P1** = 首个正式版本需要;**P2** = 迭代增强。

### 3.1 智能体团队(P0)

#### FR-1.1 角色体系
系统提供一组人格化智能体,每个具备:唯一名字、头像、一句话定位、第一人称自述、明确能力边界、可被 `@` 的 handle。

v1 角色集(在 Atoms 八角色基础上精简合并):

| Handle | 角色 | 职责 | 优先级 |
|---|---|---|---|
| `@lead` | 团队负责人 | 意图理解、任务拆解、分派、进度汇总、联网查资料 | P0 |
| `@eng` | 全栈工程师 | 编码、构建、Bug 修复、部署 | P0 |
| `@pm` | 产品经理 | 需求澄清、PRD 生成、功能优先级 | P1 |
| `@arch` | 架构师 | 技术选型、数据模型、API 设计 | P1 |
| `@data` | 数据科学家 | 数据清洗、分析、图表、抓取、样例数据生成 | P1 |
| `@research` | 深度研究员 | 多源检索 + 来源核验 + 结构化报告 | P1 |
| `@seo` | SEO 专家 | meta 标签、sitemap、多语言 SEO 内容 | P2 |
| `@ads` | 投放代理 | 广告文案、campaign 计划、转化追踪 | P2 |

**验收标准**
- AC-1.1.1 每个角色有独立的 system prompt、可用工具集与模型偏好配置
- AC-1.1.2 用户不指定角色时,`@lead` 在 3 秒内给出分派方案并在 UI 中展示"派给了谁、为什么"
- AC-1.1.3 每条消息在 UI 上明确标注发言者身份(头像 + 名字)

#### FR-1.2 `@` 提及与并行执行
- 输入 `@` 唤出角色选择下拉,支持在一条消息中提及多个角色
- 被提及的多个角色 **并行独立执行**,各自产出独立结果块
- 单智能体模式下输入 `@` 时,提示用户切换到团队模式

**验收标准**
- AC-1.2.1 同时 @ 三个角色时,三个执行流并行推进,UI 分栏或分块展示各自进度
- AC-1.2.2 任一角色失败不阻塞其余角色

### 3.2 运行模式(P0)

#### FR-2.1 模式矩阵

| 模式 | 参与者 | 定位 | 优先级 |
|---|---|---|---|
| **Solo** | 仅 `@eng` | 快、省额度,简单站点与原型 | P0 |
| **Team** | 全部角色 | 复杂需求,支持 `@` 提及、研究、SEO | P0 |
| **Race** | 同一 prompt 跑 N 个模型/N 个版本 | 并行择优,提高成功率 | P2 |
| **Research** | `@research` 主导 | 生成带引用溯源的专业报告 | P1 |

**验收标准**
- AC-2.1.1 模式切换入口在输入框固定位置,切换后新会话记忆该选择
- AC-2.1.2 项目进行中可随时切换模式,不丢失上下文
- AC-2.1.3 切换模式时显式展示"该模式预计消耗倍率"(如 Team ≈ 3× Solo)
- AC-2.1.4 Race 模式给出明确的互斥提示(与后端集成项目、与 Research 模式)

> **对 Atoms 的改进点**:Atoms 的 Deep Research "每条消息后自动关闭需手动重开",是明显的体验缺陷。
> Forge 的 Research 模式一旦开启即在会话内保持,直到用户显式关闭。

### 3.3 多模型路由(P0)

#### FR-3.1 模型选择
- 默认 `Auto`:由路由策略按任务类型自动选模型
- 用户可手动指定;每个模型展示优势/劣势/适用场景/相对成本(1–5 星)
- Race 模式下可勾选多个模型或同一模型多实例

**验收标准**
- AC-3.1.1 模型列表以配置驱动,新增模型无需改前端代码
- AC-3.1.2 每次执行结束后,在结果块显示实际使用的模型与消耗额度

### 3.4 构建工作区(P0)

#### FR-4.1 对话区
- 富文本输入,支持 `#` 引用工作区文件、`@` 提及角色
- 附件:文件/文件夹上传(单文件 ≤100MB)、图片粘贴上传、zip 导入既有项目
- **随时打断**:执行中可暂停;可在执行中追加纠正指令,智能体在下一步吸收
- 每条智能体消息提供 `...` 菜单:重试、复制、反馈上报

**验收标准**
- AC-4.1.1 点击暂停后 5 秒内实际停止工具调用,不产生额外额度消耗
- AC-4.1.2 上传的资产以 `# 文件名` 形式在输入框中呈现,后续可通过 `#` 自动补全再次引用

#### FR-4.2 实时预览器(App Viewer)
- 构建完成后自动展示可交互预览
- 设备视图切换:Desktop / Tablet / Mobile
- 新标签页打开、手动刷新
- **点选即改**:点击预览中任意元素,弹出属性面板可改颜色、间距、字体、布局、文本,改动即时生效并回写代码
- **资产库**:内置图标、图片、UI 组件可直接插入
- 也支持纯自然语言描述改动

**验收标准**
- AC-4.2.1 预览加载超过 60 秒时展示明确的诊断入口(查看日志 / 刷新 / 上报)
- AC-4.2.2 可视化编辑的每次改动生成一条可撤销的代码变更记录
- AC-4.2.3 元素点选到属性面板弹出的延迟 < 200ms

#### FR-4.3 代码编辑器
- 文件树浏览、语法高亮、**变更行与新文件高亮标注**
- 复制代码、单文件下载、目录打包下载、全量导出 zip
- 直接编辑代码为付费权益(Solo 版只读)
- 单文件预览运行(如 `index.html`)

#### FR-4.4 执行日志面板
- **Terminal**:实时流式展示智能体动作(建文件、写代码、跑命令、报错)
- **Console**:构建期日志与运行时错误,错误含描述、文件、行号、调用栈

**验收标准**
- AC-4.4.1 日志流式输出延迟 < 1 秒
- AC-4.4.2 长日志虚拟滚动,10 万行不卡顿

#### FR-4.5 一键修错(Issue Report)
- 构建出错时角落弹出通知:错误摘要 + `Resolve` 按钮 + 展开详情
- 点 `Resolve` 由智能体自动定位并修复,预计 1–3 分钟
- **执行中禁用按钮**,防止重复提交产生并发任务
- 修复完成自动刷新预览
- 修不好时提供一键上报(自动携带会话链接 + 错误日志 + 截图)

**验收标准**
- AC-4.5.1 `Resolve` 在任务进行中处于 disabled 状态并显示进度
- AC-4.5.2 上报表单自动填充诊断上下文,用户只需补充一句描述

### 3.5 版本与分叉(P0)

#### FR-5.1 版本历史
- 每次构建产出一个版本快照(代码 + 资产 + 元信息)
- 版本列表可预览、可对比、可回滚
- 发布时可选"始终最新"或"锁定指定版本"

#### FR-5.2 Fork(对标 Remix)
- 把任意项目/任意历史版本复制成新会话,保留代码、重置对话历史
- 入口:社区广场、项目内版本框、历史版本列表
- 双重价值明确告知用户:① 复用他人作品 ② **长会话降本**(超过阈值时主动提示"当前会话已有 N 个版本,Fork 可降低约 X% 的单次请求成本")

**验收标准**
- AC-5.1.1 Fork 出的新会话与原会话完全隔离,互不影响
- AC-5.1.2 会话版本数超过 10 时,系统主动提示 Fork 降本
- AC-5.1.3 明确告知用户 Fork 后哪些集成需要重新授权

> **对 Atoms 的改进点**:Atoms 接入自研 Cloud 后 **禁用了历史版本**(避免库表与代码错配)。
> Forge 应通过 **数据库迁移脚本随版本一起快照** 来保留版本能力,而非直接砍掉功能。

### 3.6 团队协作(P1)

#### FR-6.1 工作区
- 注册即有个人默认工作区;付费版可邀请成员(v1 上限 20 人,而非无限)
- 邮箱批量邀请,状态流转 `邀请中 → 已加入`
- 顶部切换器在多工作区间切换

#### FR-6.2 角色权限

| 权限 | Viewer | Editor | Owner |
|---|---|---|---|
| 查看项目与会话 | ✅ | ✅ | ✅ |
| 与智能体对话 | ❌ | ✅ | ✅ |
| 编辑代码 / 可视化编辑 | ❌ | ✅ | ✅ |
| 发布 / 下线 | ❌ | ✅ | ✅ |
| 修改工作区信息 | ❌ | ❌ | ✅ |
| 邀请 / 移除成员 | ❌ | ❌ | ✅ |
| 管理套餐与计费 | ❌ | ❌ | ✅ |
| 管理集成与密钥 | ❌ | ❌ | ✅ |

> **对 Atoms 的改进点**:Atoms 只有 Owner/Editor 两档,缺少只读角色,导致"给客户看进度"必须开放编辑权。Forge 增加 Viewer。

#### FR-6.3 实时协同
- 同一会话支持多人同时在线与智能体交互
- 消息按发送者头像/昵称区分
- 显示在线成员与正在输入状态

#### FR-6.4 集中计费
- 工作区共享额度池
- 成员级用量明细(谁消耗了多少)

### 3.7 发布与分发(P0)

#### FR-7.1 发布
- 一键生成稳定公开链接;发布后按钮转为"更新"
- 可下线
- 付费版可移除平台角标
- 发布配置:版本策略(最新/指定)、可见性、自定义域名

#### FR-7.2 分享与权限
- 三档可见性:**公开**(可进社区广场)/ **链接可见** / **私有**
- 一键分享到主流社交平台,带预格式化文案与 OG 预览卡
- 项目卡片可自定义封面、标题、描述、展示版本
- **发布前安全扫描**:检测代码与会话中的疑似密钥、密码、个人信息,发布公开前强制提示

**验收标准**
- AC-7.2.1 公开前的密钥扫描覆盖常见格式(AWS/Stripe/OpenAI/GitHub token、私钥 PEM 头、`.env` 内容)
- AC-7.2.2 检出敏感信息时阻断发布流程,列出具体位置供用户确认

> **对 Atoms 的改进点**:Atoms 仅在文档里 **口头提醒** 用户"分享前请自查敏感信息",没有产品化拦截。这是明确的安全缺口,Forge 必须做成强制扫描。

#### FR-7.3 社区广场
- 公开项目的展示、检索、排行、标签
- 支持一键 Fork、点赞、评论
- 项目详情页展示所用模式与模型标签
- 官方精选位与创作者激励

#### FR-7.4 域名管理
- 首次发布分配随机子域,可自定义前缀
- **绑定已有域名**:引导添加 A 记录 + TXT 校验记录,自动识别主流服务商,提供 `dig`/`nslookup` 自检命令,展示实时校验状态
- **域名购买**:对接注册商 API(如 IONOS/Namecheap)
- 多域名时设置主域,其余 301 重定向
- 自动签发与续期 TLS 证书

**验收标准**
- AC-7.4.1 DNS 配置页展示逐项校验状态(A 记录 ✅ / TXT 记录 ⏳),而非只有一个"验证"按钮
- AC-7.4.2 证书签发失败有明确原因说明与重试入口

### 3.8 后端能力(P0)

#### FR-8.1 内置 BaaS(对标 Atoms Cloud)
自动探测项目后端需求并完成配置,提供:

| 能力 | 说明 | 优先级 |
|---|---|---|
| **数据库** | 托管 Postgres,智能体可建表改表,提供可视化表编辑器 | P0 |
| **认证** | 邮箱密码 + 社交登录(Google/GitHub),会话与权限管理 | P0 |
| **文件存储** | 用户上传文件的对象存储 + CDN | P1 |
| **Serverless 函数** | 用于发邮件、调 AI、处理 Webhook 等服务端逻辑 | P0 |
| **密钥管理** | 加密存储,运行时注入,平台不可读 | P0 |
| **定时任务** | Cron 触发的后台作业 | P2 |
| **支付** | Stripe 接入,订阅与一次性收款 | P1 |
| **AI 网关** | 应用内调用 LLM 的统一入口与计量 | P1 |

**验收标准**
- AC-8.1.1 用户说"把表单数据存起来",系统自动建表、生成读写代码、接进 UI,无需用户碰 SQL
- AC-8.1.2 数据库 schema 变更随版本快照,回滚版本时同步回滚 schema(含迁移脚本)
- AC-8.1.3 每个项目的数据库网络隔离,默认拒绝外部直连

#### FR-8.2 外部 BaaS 集成(P1)
支持连接用户自有的 Supabase 项目,满足要掌控数据的用户:
- OAuth 授权 → 选择组织与项目 → 自动读取库结构/表/RLS 策略
- 提供 OAuth 绑定冲突的自助解绑指引
- 明确告知 Fork 后需要重新授权

#### FR-8.3 密钥管理(P0)
- 智能体检测到需要密钥时,在对话中弹出 **专用输入组件**(而非让用户贴进聊天)
- 密钥加密入库,运行时注入函数环境变量
- **平台侧不可解密读取**,审计日志只记录"使用了哪个密钥"不记录值
- 对话框内输入疑似密钥时主动拦截并引导到专用组件

**验收标准**
- AC-8.3.1 聊天输入框检测到疑似密钥格式时,弹出"请用安全方式添加"的引导并阻止直接发送
- AC-8.3.2 密钥值在任何日志、错误信息、LLM 上下文中均不出现

> 这是全系统最高优先级的安全需求。Atoms 已有该机制,Forge 必须至少对齐,并额外增加输入框侧的主动拦截。

#### FR-8.4 支付集成(P1)
- 自然语言描述订阅方案,自动生成价格配置表单
- 引导填入 Secret Key、各方案 Price ID、Webhook Secret
- **自动创建 Webhook 端点并回填 URL**,而不是让用户在两个控制台之间手工拷贝
- 提供测试模式与测试卡引导
- 明确告知预览环境无法测试 Webhook,必须部署后测

> **对 Atoms 的改进点**:Atoms 的 Stripe 配置流程需要用户在 Stripe 控制台和 Atoms 之间来回拷贝
> 4 类凭据与 Webhook URL,是全文档中步骤最繁琐的一节(含 15 张截图)。
> Forge 应通过 Stripe OAuth(Connect)把这个流程压缩到"授权 + 选产品"两步。

#### FR-8.5 代码托管集成(P1)
- GitHub/GitLab OAuth 授权
- 在平台内创建仓库,Push / Pull 双向同步
- 心智模型明确:平台是活跃工作区,Git 是归档与协作中心

#### FR-8.6 第三方连接器(P2)
- 统一的连接器中心:授权 → 权限审阅 → 确认连接
- 首批:Linear、Asana、Todoist、Notion、Slack
- 基于 MCP 协议接入,降低新增连接器成本
- 权限最小化:每个连接器声明所需 scope,用户可逐项批准

### 3.9 增长模块(P2)

#### FR-9.1 SEO
- `@seo` 自动生成 meta 标签、canonical URL、`sitemap.xml`、结构化数据
- 多语言 SEO 内容生成
- Google Search Console 接入引导:属性添加 → HTML Tag 验证(智能体自动插入)→ 提交 sitemap → 手动请求收录

#### FR-9.2 分析看板
- GA4 授权接入,自动检测并注入跟踪脚本
- 流量来源、页面行为、转化、高价值访客
- SEO 运营指标:收录页数、点击、曝光、CTR、平均排名

#### FR-9.3 广告投放
- 自动抽取产品与落地页信息 → 生成广告文案与投放计划 → 用户审批 → 上线监控
- 转化追踪自动配置
- 看板:CTR、花费、转化、受众画像
- 强制的预算确认环节与"这会花真钱"的显式告知

**验收标准**
- AC-9.3.1 任何产生真实广告花费的操作,必须有独立的二次确认弹窗,展示日预算与预计上限
- AC-9.3.2 域名与投放活动的绑定关系在 UI 中可见,Fork 时明确提示需要解绑重绑

### 3.10 计费体系(P0)

#### FR-10.1 额度(Credits)
- 三种来源:每日赠送、订阅额度、奖励额度(推荐/兑换码/客服补偿)
- 扣减优先级:每日 → 订阅 → 奖励
- 每日额度定时重置,设月度累计上限
- 结转规则:可结转的额度只保留一个计费周期

**验收标准**
- AC-10.1.1 **执行前预估**:提交任务前展示预计消耗区间,余额不足时提前拦截并给出充值入口
- AC-10.1.2 每次执行后展示实际消耗明细(哪个角色、哪个模型、多少额度)
- AC-10.1.3 额度页展示消耗趋势与 Top 消耗项目

> **对 Atoms 的改进点**:Atoms 全文档有 7 篇在解释 credits 规则(daily/subscription/bonus 三类
> × 结转规则 × 扣减顺序 × 触顶行为),用户理解成本极高,且文档内部还出现 15 与 7.5 credits/天的自相矛盾。
> Forge 应做到 **规则更简单 + 事前可预估**:任务提交前就告诉用户要花多少,而不是事后对账。

#### FR-10.2 订阅套餐

| | Free | Pro | Max |
|---|---|---|---|
| 月额度 | 仅每日赠送 | 中档,分档可选 | 高档,分档可选 |
| 磁盘 | 2 GB | 10 GB | 100 GB |
| 算力 | 基础 | 基础 | 2× |
| 私有项目 | ❌ | ✅ | ✅ |
| 源码下载 | ❌ | ✅ | ✅ |
| 去角标 | ❌ | ✅ | ✅ |
| 直接改代码 | ❌ | ✅ | ✅ |
| Race 模式 | ❌ | ❌ | ✅ |
| 团队席位 | 1 | 20 | 20 |
| 内置后端项目数 | 1 | 无限 | 无限 |

- 年付折扣,额度按 12 期发放,周期内可结转
- 升级即时生效、只补差价、不重置计费周期
- 降级在当前周期结束后生效;磁盘缩水提前告知并给出清理引导

#### FR-10.3 用量钱包(后付费)
- 预付余额 + Cloud 免费额度 + AI 免费额度三类
- 多渠道充值,支持自动充值
- **风控双闸**:余额低于阈值告警;月度上限触顶后可选"暂停应用"或"仅通知"
- 用量看板:按项目、按类型(计算/存储/网络/AI)拆分
- 交易流水与用量明细分离展示
- 坦诚披露:后付费与按小时计费导致实际账单可能略超月度上限

**验收标准**
- AC-10.3.1 应用因余额耗尽被暂停前,至少发出两次提前告警(阈值告警 + 即将暂停告警)
- AC-10.3.2 暂停原因在项目页显著位置展示并提供一键充值恢复

### 3.11 帮助中心(P1)

## 4. 关键流程

### 4.1 首次创建到发布(黄金路径)

```
着陆页输入想法
   ↓
[可选] Prompt 优化建议(省额度)
   ↓
选择模式(默认 Solo)+ 模型(默认 Auto)
   ↓
@lead 拆解任务 → 分派 → UI 展示分派理由
   ↓
各角色并行/串行执行 ── Terminal 实时流式日志
   ↓
构建完成 → App Viewer 自动展示预览
   ↓
┌── 有错? → Issue Report 弹出 → 点 Resolve → 自动修复 → 回到预览
│
├── 要改样式? → 点选元素 → 属性面板调整 → 即时生效
│
├── 要改逻辑? → 对话描述 / 直接改代码
│
└── 要存数据? → 系统探测到需求 → 自动开通内置后端 → 建表 → 接进 UI
   ↓
发布前安全扫描(密钥/隐私)
   ↓
Publish → 分配子域 → [可选] 绑自定义域名
   ↓
[可选] SEO 优化 → 提交搜索引擎 → 接入分析 → 投放广告
```

### 4.2 错误恢复流程

```
构建失败
   ↓
捕获错误(类型/文件/行号/堆栈)
   ↓
角落通知:摘要 + Resolve + 展开详情
   ↓
用户点 Resolve(按钮立即 disabled)
   ↓
@eng 读取错误上下文 → 定位 → 修复 → 重新构建
   ↓
┌── 成功 → 预览自动刷新 → 通知消失
│
└── 失败(≤2 次自动重试)→ 升级提示:
      建议 A:回滚到上一个可用版本
      建议 B:换模型重试
      建议 C:一键上报(自动附会话链接+日志+截图)
```

### 4.3 额度不足流程

```
用户提交任务
   ↓
预估消耗 vs 当前余额
   ↓
┌── 充足 → 直接执行,执行后展示实际消耗
│
├── 勉强够 → 提示"预计消耗 X,余额 Y,可能不足以完成" → 用户确认
│
└── 不足 → 拦截,不启动任务(不产生半成品)
      → 展示:升级套餐 / 充值钱包 / 等待明日赠送 / 切换到更省的模式
```

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| **性能** | 首屏 LCP < 2.5s;对话首 token < 3s;日志流延迟 < 1s;预览构建 P50 < 30s / P95 < 120s |
| **可用性** | 核心链路 99.9%;单个智能体故障不影响其他角色;构建沙箱崩溃自动重建并保留工作区 |
| **安全** | 沙箱强隔离(网络+文件系统+资源配额);密钥加密静态存储 + 运行时注入;发布前敏感信息扫描;所有第三方授权走 OAuth 最小 scope;审计日志留存 180 天 |
| **隐私** | 用户代码默认不用于模型训练;数据删除请求 30 天内彻底执行;明确的数据驻留地披露 |
| **可扩展** | 沙箱与模型均为横向可扩池;新增模型/角色/连接器纯配置驱动 |
| **成本** | 单次构建的基础设施成本可归因到项目与用户;沙箱空闲自动休眠回收 |
| **可访问性** | WCAG 2.1 AA 为目标(完整验证需人工辅助技术测试与专家评审) |
| **国际化** | UI 与文档架构支持多语言;时区/货币本地化 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 沙箱逃逸导致平台被攻击 | 致命 | 强隔离容器 + seccomp/AppArmor + 出站白名单 + 资源硬限 + 定期红队演练 |
| 用户密钥泄漏 | 致命 | 专用输入组件 + 加密存储 + 运行时注入 + 输入框主动拦截 + 日志脱敏 |
| 公开分享导致用户隐私外泄 | 严重 | 发布前强制扫描 + 阻断式提示 |
| 模型 API 成本失控 | 严重 | 事前预估 + 硬额度拦截 + 月度上限 + 单任务 token 上限 |
| 生成代码质量不稳定 | 严重 | 构建后自动 lint/typecheck/冒烟测试;失败自动进入修复循环;Race 模式兜底 |
| 上游模型 API 中断 | 中等 | 多供应商冗余 + 自动降级路由 |
| 版本与数据库 schema 错配 | 中等 | 迁移脚本随版本快照,回滚时一并回滚(不采用 Atoms "禁用历史版本"的做法) |
| 计费规则复杂引发争议 | 中等 | 规则简化 + 事前预估 + 明细可查 + 争议处理 SLA |

## 9. 开放问题

1. **自研 BaaS 还是全托外部?** 自研控制体验但研发与运维成本高。建议 M3 先做"托管 Postgres + 函数 + 认证"的最小自研集,存储与支付先接外部。
2. **Race 模式是否值得做?** Atoms 将其限定给最高档用户,说明成本高。建议放到 M5 之后按数据决策。
3. **社区广场的冷启动**:没有内容就没有 Fork 价值。是否需要官方先产出一批高质量模板?
4. **免费额度的力度**:太小无法体验完整链路,太大成本不可控。需要基于单次构建实际成本建模后定档。
5. **代码所有权与许可**:生成代码的版权归属、商用许可、第三方依赖合规,需要法务先行明确。
