# 13 — 真实模型上的 prompt 健康度

**What to build:** 前面十二张票的测试全部用**脚本化的假模型**驱动。
这保证确定性、速度和零成本，但漏掉一整类故障：**调度逻辑全对，但模型不再配合**。

这张票加一组打真实模型的测试，只问一件事：**"这个 prompt 还能让模型做对事吗？"**

关键在于**断言要宽**。这不是测行为，是测健康度——
所以断言"Alex 至少产出了一个 `write_file` 调用"，而不是断言它写了什么内容。
宽断言让测试不会被模型的正常波动搞红，同时仍能抓住 prompt 退化。

**Blocked by:** 04 — Emma 先规划，文件树骨架填入

**Status:** done

- [ ] 有一组独立的测试，打真实模型（与脚本化测试分开，可以单独跑、单独跳）
- [ ] 测试数量控制在 3–5 个，每个都是一次真实的端到端调用
- [ ] **Mike 能分派**：给一句模糊需求，断言它调用了 Emma（不是自己写代码）
- [ ] **Emma 能规划**：断言产出的文件清单是非空的、路径看起来像文件
- [ ] **Alex 能写文件**：断言至少一个 `write_file` 调用，内容非空
- [ ] **Alex 能修错**：给一个注入的构建错误，断言它产出了新的 `write_file` 而不是重复同一个内容
- [ ] **工具 schema 还匹配**：断言工具调用没有因为 schema 变化被模型拒绝
- [ ] 断言全部是**宽断言**——不断言具体文字、不断言文件数、不断言文件名
- [ ] 这类测试不阻塞 CI 的常规运行（单独的命令，或标记为可选）
- [ ] 跑一次确认全绿，并在提交信息里记录实际花费的 token 量级

**注**：这类测试的价值会随时间衰减（模型升级、prompt 改动），
这正是它存在的意义——它是 prompt 退化的报警器，不是功能测试。
