## Problem Statement

一个陌生人打开 Forge，想做一个东西，但不会写代码。

现在他面对的是一个空页面。他唯一能做的是自己学 React，或者找一个已经会写代码的人。
市面上有别的 AI 建站工具，但它们要么要求注册、要么要求付费、要么得懂技术术语才能用。

**他需要的不是"一个 AI 对话框"，是"一个能拿到东西的过程"**——
他说清楚想要什么，然后**看着它被建出来**，中途随时能喊停、能改方向、
能在失败时知道发生了什么，最后拿到一个**真的能跑起来、能点、能用的应用**。

这个"看着它被建出来"是核心。等待时间里如果只有一个转圈，
用户无法判断系统是在工作还是卡死了，也没法在发现方向不对时及时喊停——
而生成一次要花几分钟和真实成本。

---

## Solution

用户描述想要的东西，Forge 的 agent 团队把它建出来，用户在右侧实时看着它成形。

**一次完整生成**：Mike（负责人）理解意图 → Emma（产品经理）拆出文件清单
→ Alex（工程师）逐个写入 → 装依赖 → 构建 → 出预览。
文件树从**灰色占位**开始长出，每个文件被填充时变成进行中、再变成完成——
用户看到的是"4 个文件，正在写第 2 个"，而不是一个转圈。

**失败时说人话**。构建报错时 Alex 自己修（最多 3 次），
错误以"出了点问题，Alex 正在自己修"呈现，原始错误折叠在后面。
超过 3 次就停下来说清楚，不无限转圈。

**随时能喊停**。中断后已写入的文件**保留**，额度按实际用量结算、冻结差额退还，
那条未完成的助手消息标记为 `interrupted`——下次继续时模型知道上次到哪了。

**能多轮改**。应用跑起来后继续说"把卡片改成三列"，Alex 只改需要的文件，
并告诉用户"本轮改了 1 个文件"。第二轮修改跳过依赖安装（没有新依赖时）。

**能拿走**。一键导出 zip。

## User Stories

### 首次生成

1. 作为一个不会写代码的人，我想用自然语言描述我想要的东西，这样我就不需要学编程或写技术规格
2. 作为一个刚打开 Forge 的人，我想看到几个具体的例子说明这里能做什么，这样我就知道该从哪句话开始
3. 作为一个还没决定要不要用的人，我想知道不需要注册就能试，这样我愿意先试一下再决定
4. 作为一个提交了描述的人，我想立刻看到系统开始工作，这样我不会以为页面坏了或我没点到
5. 作为一个等待的人，我想看到团队里谁在做什么（Mike 在理解、Emma 在拆解、Alex 在写），这样我对"一个团队在给我干活"有实感
6. 作为一个等待的人，我想在 Emma 拆完之后**立刻看到文件清单**，这样我知道总共要做几件事、大概要等多久
7. 作为一个等待的人，我想看到文件树里的每个文件从"待生成"变成"正在写"再变成"完成"，这样进度是真实可验证的，而不是一个编出来的进度条
8. 作为一个等待的人，我想看到正在写入的文件的**内容逐行出现**，这样我能确认它真的在写我要求的东西
9. 作为一个等待的人，我想在不确定时展开活动日志看到完整事件流，这样我能自己判断它在干什么（但默认不展开，因为我不需要看日志）
10. 作为一个等待的人，我想看到当前动作的语义化描述（"正在写 src/App.tsx"），而不是终端输出
11. 作为一个等待的人，我想在应用开始构建时知道进入了新阶段，这样长时间等待不会让我以为卡住了
12. 作为一个等待的人，我想在依赖安装、数据库迁移、安全检查这些中间步骤有可见的状态，这样十几秒的静默不会让我刷新页面
13. 作为一个等了一会儿的人，我想在预览就绪时看到它自动出现，这样我不需要手动点刷新
14. 作为一个看到预览的人，我想能切换桌面 / 平板 / 手机三种视口，这样我知道它在不同尺寸下什么样
15. 作为一个看到预览的人，我想能点里面的按钮、填里面的表单、用里面的功能，这样我确认它真的能跑而不只是一张图
16. 作为一个看到预览的人，我想能一键在新标签页打开它，这样我可以在真实窗口里看
17. 作为一个看到预览的人，我想看到沙箱正在恢复时的提示，这样返回一个旧工作区时约 1 秒的空白不会让我以为坏了

### 失败与自修复

18. 作为一个遇到构建失败的人，我想知道系统正在自己修，而不是看到一个红色的技术栈
19. 作为一个遇到构建失败的人，我想看到一句人话说明出了问题，原始错误折叠在后面，这样我不懂技术也能知道大概是什么事
20. 作为一个遇到构建失败的人，我想知道它最多自己修几次，这样我有心理预期，不会无限等下去
21. 作为一个遇到反复失败的人，我想在超过重试上限后被明确告知并停止，而不是无限转圈
22. 作为一个遇到反复失败的人，我想在失败后**保留已经写好的文件**，这样重试不用从零开始
23. 作为一个遇到失败的人，我想看到"失败原因 + 下一步建议"，这样我知道能做什么而不只是知道失败了

### 安全检查

24. 作为一个要生成带数据库的应用的人，我想知道系统会自动检查数据隔离策略是否安全，这样我不需要自己懂 RLS
25. 作为一个安全检查没通过的人，我想被明确告知**这是停下等你确认，不是自动重试**，这样我不会在不知情的情况下继续
26. 作为一个安全检查没通过的人，我想知道"已回滚、未对外暴露任何数据"，这样我知道这次失败是安全的
27. 作为一个安全检查没通过的人，我想能选择"让 Alex 重写"或"先看看详情"，这样我能决定下一步
28. 作为一个安全检查没通过的人，我想看到检测到的具体是哪条策略有问题，这样我能理解（即使我看不懂代码，我也能看出它指的是哪个地方）

### 中断

29. 作为一个生成到一半的人，我想能立刻停止，这样我可以在发现方向不对时省钱省时间
30. 作为一个停止之后的人，我想已经生成的文件**保留下来**，这样我不会因为一次停止而丢掉进度
31. 作为一个停止之后的人，我想只按**实际用量**结算、冻结的部分退还，这样我为没发生的事不付钱
32. 作为一个停止之后的人，我想能看到"继续刚才的"和"换个方向重来"两个选项，这样我不用自己想怎么接上
33. 作为一个停止之后又继续的人，我想模型知道上次在哪停的，这样它不会重复已经做过的事

### 多轮修改

34. 作为一个已经有预览的人，我想继续用自然语言改它（"把卡片改成三列"），这样我不需要重新生成整个应用
35. 作为一个要多轮修改的人，我想在改之前知道**大概会动哪些文件**，这样我不会担心它把别的部分也改了
36. 作为一个多轮修改后的人，我想被明确告知"本轮改了 1 个文件"，因为我没有 diff 视图，这是我知道改动范围的唯一方式
37. 作为一个多轮修改后的人，我想在没有新依赖时**跳过依赖安装**，这样每轮修改不用白等几秒
38. 作为一个多轮修改后的人，我想预览自动刷新到新版本，这样我能立刻看到改动效果
39. 作为一个多轮修改的人，我想我的对话历史在同一会话里保持连续，这样我可以说"刚才那个再改一下"而不用重复上下文

### 拿走成果

40. 作为一个做完了的人，我想一键下载 zip 拿到全部代码，这样我能把它放到别处或者交给别人看
41. 作为一个下载了 zip 的人，我想它包含能直接跑起来的完整项目（不只是源文件），这样我拿到手不需要再猜怎么运行

### 状态与布局

42. 作为一个在看生成过程的人，我想对话和预览**同时可见**，这样我不需要来回切换来判断我上一句话的效果
43. 作为一个刚提交、还没开始写文件的人，我想预览区先收起来，这样我不会盯着一个空白画布等
44. 作为一个在手机上打开的人，我想对话占满屏幕、预览可以全屏展开，这样小屏上我至少能读和改
45. 作为一个看界面的人，我想顶栏能看到全局状态（生成中 / 运行中 / 需要确认），这样我在看别处时也知道它进行到哪了

### 错误恢复与边界

46. 作为一个遇到沙箱启动失败的人，我想被明确告知并可以选择重试，而不是看着一个卡住的加载状态
47. 作为一个回到很久没用过的工作区的人，我想它能自己恢复，这样我不需要理解"沙箱"这个概念
48. 作为一个工作区已被回收的人，我想被明确告知需要重新生成，而不是遇到一个坏掉的预览
49. 作为一个提交了空白或只有空格的内容的人，我想它不被当成一次生成，这样我不会白花额度
50. 作为一个提交了超长内容的人，我想收到明确的长度限制提示
51. 作为一个网络断了的人，我想在重连后看到当前真实状态，而不是从我断掉的地方继续播一个过期的动画

## Implementation Decisions

### 模块

**Orchestrator** —— 生成循环的核心，是本次唯一的测试接缝（见 Testing Decisions）。

对外只有一个接口：

```
run(sessionId, userInput) → AsyncIterable<ForgeEvent>
```

输入是会话 ID 和用户输入，输出是一个 SSE 事件流。**它不知道 HTTP 的存在**，
也不知道 React 的存在。所有循环逻辑——角色分派、骨架先行时序、有界自修复、
中断处理、门控转交——都在这个接口之内，可被断言。

**Sandbox adapter** —— 包住 E2B 的全部调用（创建、写文件、执行命令、暂停、恢复、杀掉）。
Orchestrator 只见这个接口，不见 E2B SDK。

**Model adapter** —— 包住对 LLM 的调用。Orchestrator 只见"给角色和消息、拿回流式响应"。

两个 adapter 的存在理由相同：**让 orchestrator 可以在不接触真实沙箱和真实模型的情况下被完整测试**。

### 角色

三个角色，各自是一个声明式配置：`instructions`（职责与人格）、`tools`（白名单）、`model`。

| 角色 | 工具白名单 | 职责 |
|---|---|---|
| Mike（`@lead`） | 派发类（调用下游角色） | 理解意图、分派、汇总、呈现冲突 |
| Emma（`@pm`） | 只读 | 需求 → 结构化功能描述 + 文件清单 |
| Alex（`@eng`） | `write_file`、`run_command` | 实现 |

**只有 Alex 能写文件**。这是白名单，不是约定。

新增角色 = 加一份配置，不改调度代码。

### 上下文

**三个角色共享同一个会话历史**，仅由各自的 instructions 区分。
不做隔离是有意的：设计信息应当流向工程实现，Alex 看到 Emma 的需求讨论是收益。

分流机制是 supervisor 在每轮开始时**汇总并重述**意图（生成完整 prompt）。
这个重述同时服务于两个目的：

1. **上下文隔离**——每个下游角色看到一个聚焦的 prompt，而不是全部历史
2. **prompt 稳定**——同一输入产出同一 prompt，这是后续做版本回滚时重放的前提

风险已知并接受：若日后出现真实污染，可加摘要注入，不需要重写 orchestrator。

### 并行

按操作类别分区，不是一律并行：

- **只读分析类**（未来加 `@research` 等）：自由并行
- **设计推理类**（`@pm`、`@arch`）：**串行**
- **工作区写入**（`@eng`）：**单写者**

MVP 只有三个角色，实际路径是 `@pm` → `@eng` 串行。
但接口要按并行设计：调用方从 `await` 单个改为收集多个 promise 即为并行，
对角色内部完全透明。

**为什么设计推理不并行**：两个角色推理的是同一个设计，并行会产出两份半一致的答案
外加一个协调问题——那是我们强行并行造出来的冲突，不是真实分歧。

**为什么写入必须单写者**：文件系统写入没有 base。丢失的写入是静默的——
没有报错、没有冲突标记、没有失败的测试。

### 生成协议

**原生 tool call，不是 XML 协议**。

`write_file` 的输入用 schema 校验（路径 + 内容）。这消掉了整类调试时间——
畸形或截断的 XML 的失败模式不存在了。

"代码逐行出现"的观感不受影响：工具调用的参数有流式 delta 事件，
可以保留逐行写入的视觉。

### 事件契约

Orchestrator 显式发事件，前端纯渲染。顶层事件类型：

| 事件 | 载荷 | 含义 |
|---|---|---|
| `agent_started` | `agentHandle`, `messageId` | 某角色开始工作 |
| `text_delta` | `agentHandle`, `delta` | 角色的文字输出增量 |
| `tool_call_start` | `toolName`, `toolCallId` | 工具调用开始 |
| `tool_input_delta` | `toolCallId`, `argsDelta` | 工具参数流式增量（逐行写入的观感来源） |
| `tool_result` | `toolCallId`, `result` | 工具调用返回 |
| `agent_done` | `agentHandle`, `creditsUsed` | 某角色完成 |
| `error` | `agentHandle`, `message` | 错误 |

每个事件都带 `agentHandle`，这使前端在并行时天然分路渲染，无需改动。

**不要往这个列表里加东西。** 三个高频瞬时进度事件走另一条路：

| 进度事件 | 为什么需要 |
|---|---|
| `plan_ready` | 骨架先行的触发点。没有它，首个文件写完前只有 spinner |
| `gate_started` | 两道门控合计 5–15 秒，静默会被当成卡死 |
| `sandbox_state` | 沙箱恢复约 1 秒，不能无声 |

这三个用 **transient chunk**（跳过持久化的自定义事件）发射：
不占存储、刷新后不重现、不进顶层事件类型。

理由：它们高频、量大、只在当下有意义。混进主事件流会让持久化层
为一堆转瞬即逝的状态付代价。

### 状态机

生命周期状态及其转移（**来自原型**，`prototypes/generation-loop.mjs`，6 个变体全部跑通）：

```
idle → submitting → reserving → sandbox_booting → understanding → planning
     → generating → [installing] → [migrating → gating] → building → previewing
     → settling → idle_iterate ⟲

分支：
  submitting  → blocked_credits          额度不足，任务不启动
  generating  → interrupted              用户停止
  generating  → building                 第二轮修改跳过依赖安装 ★
  building    → failed → autofixing ⟲    有界重试，上限 3 次
  autofixing  → gave_up                  超上限，停下并报告
  gating      → gate_failed              安全门控拒绝，不自动重试
```

★ 这条边是跑第二轮的变体才发现的。没有它每轮修改白等一次安装。

**`gating` 和 `building` 是不同性质的失败**——这是状态机里最重要的区分：

- **构建失败是技术问题**，自修复合理，最多 3 次
- **门控失败意味着数据隔离策略不安全**，自动重试有掩盖问题的风险，
  必须停下等用户确认

用户不该在不知情的情况下拿到一个"看起来成功了"但实际不安全的应用。

### 骨架先行的时序

**只在首轮**：

1. Emma 出 spec
2. **立刻**给出文件清单（`plan_ready`）
3. 文件树以灰色占位全部长出
4. Alex 逐个填充：`待生成` → `正在写` → `完成`

代价是多一次 LLM 往返（约 1.8 秒），换来等待过程有形状。
**后续修改不预出清单**，直接开写——修改范围小，且用户已有预览可看，焦虑低。

进度是**真实信号**，不是假进度条：文件数是已知分母。
不做假进度条。

### 状态可见性三层

| 层次 | 内容 | 更新频率 | 默认 |
|---|---|---|---|
| 顶栏 | 全局状态（生成中 / 运行中 / 需要确认） | 状态机迁移时 | 可见 |
| 消息头部 | 当前动作（"正在写 src/App.tsx"） | 每个工具调用 | 可见 |
| 活动日志 | 完整事件流 | 流式 | **折叠** |

第三层默认折叠：非技术用户不需要看日志，但需要**知道日志存在**——
可展开 = 可验证。

**这三层不要合并。**

### 中断语义

中断时：

- 已写入的文件**全部保留**
- 那条未完成的助手消息**保留并标记 `interrupted`**
- 额度按实际用量结算，冻结差额退还
- 下一轮 prompt 里明确告知"上一轮在此处被中断"

不做摘要改写——要额外一次 LLM 调用，不值。标记比删除便宜，且模型知道
"上次到哪了"直接提升续写质量。

**沙箱侧不需要写恢复逻辑**：E2B 的 auto-resume 在请求到达时自动唤醒暂停的沙箱。
但沙箱必须设 `onTimeout: 'pause'`，否则超时会**销毁**而不是暂停。

### 界面布局（状态维度）

采用双栏分屏为主形态，但吸收"可收起"：

- **生成早期（understanding / planning）预览收起**——那时对话是唯一有信息量的东西
- **首个文件写入后展开预览**
- 移动端退化为对话单栏，预览全屏覆盖
- 空状态：三个具体样例 + "不需要写代码，也不需要注册"

预览区用 iframe 嵌入沙箱的公开 URL。**该 URL 的可嵌入性已实测确认**
（响应头 `access-control-allow-origin: *`，无 `X-Frame-Options`、无 CSP `frame-ancestors`）。

布局的完整对比原型见 `prototypes/ui-layout.html`，三个结构性方案可切换。

### 导出

从沙箱文件系统打包 zip，浏览器下载。
产物是**能直接跑起来的完整项目**，不只是源文件。

### 额度交互

本 spec 只依赖额度的**接口**，不实现计量逻辑（那是 `forge-accounts`）：

- 生成前预留，完成后按实际结算退差
- 额度不足进入 `blocked_credits`，任务不启动
- 中断时按实际用量结算

### 部署形态

长驻单机（Next.js 与 orchestrator 同进程）。
**不使用 Serverless**：SSE 继承函数时长限制，而一次完整生成链 1–3 分钟起。

## Testing Decisions

### 接缝：只有一个

**Orchestrator 的 `run()` 是唯一接缝。**

```
测试 → Orchestrator.run(sessionId, userInput)
         ├─ 伪造 Sandbox（内存文件系统）
         └─ 伪造 Model（脚本化 tool call 序列）
```

这是能覆盖全部循环逻辑的**最高**接缝。它下面的沙箱和模型都是 adapter，
在测试中被替换掉——测试跑在毫秒级、零成本、完全确定性。

**不额外开 HTTP 接缝**。SSE 管道的问题会在 `forge-accounts` 那组的
端到端测试里被覆盖到，不值得为它单独开一个接缝。

### 什么算好测试

**只测外部行为，不测实现细节。**

外部行为 = 从 `run()` 返回的那个事件流里能看到的东西：

- 事件的**顺序**（`agent_started` Mike → Emma → `plan_ready` → Alex）
- 事件的**内容**（`tool_call_start` 的 toolName 是 `write_file`）
- **状态转移**（构建失败后出现 `autofixing` 相关事件，且最多出现 3 次）
- **沙箱的终态**（中断后文件系统里保留了什么）

**不测**：内部函数调用、私有方法、事件之间的实现细节、具体的 prompt 文本。

理由：这些是我们要能自由改动的东西。一个测试如果因为重构了 orchestrator
内部而变红，它测错了东西。

### 测试的两类

**第一类：状态机路径（约 90% 的测试）**

用脚本化的 model fixture 驱动。每个 fixture 是一段预设的 tool call 序列，
断言的是"给定这个序列，事件流应该长这样"。

要覆盖的路径：

| 路径 | 断言什么 |
|---|---|
| 顺利路径 | 事件顺序正确；`plan_ready` 在首个 `write_file` **之前** |
| 构建失败 → 自修复 | 出现重试；重试次数 ≤ 3；文件保留 |
| 自修复超限 → 放弃 | 出现 `gave_up` 语义；停止发事件；不再重试 |
| 门控失败 | 出现 `gate_failed` 语义；**不出现任何重试** |
| 中断 | 已写文件全在；消息标记 `interrupted`；结算按实际用量 |
| 第二轮修改 | **不出现依赖安装**；只写变更的文件 |
| 额度不足 | 任务不启动；`write_file` 一次都没被调用 |

**第二类：prompt 健康度（3–5 个测试）**

打真实模型，确认 prompt 没写坏。这类测试测的是**"模型还会不会用这些工具"**，
不是测行为——所以断言要宽（例如"Alex 产出了至少一个 `write_file` 调用"），
不要断言具体内容。

理由：纯脚本化会漏掉 prompt 退化——调度逻辑全对，但模型不再配合。
纯真实模型则慢、会 flake、每次 CI 花钱。

### 不测什么

- **不测 E2B SDK 本身**。它是外部系统，我们测自己的 adapter 边界。
- **不测 LLM 输出质量**（"这个应用写得好不好"）。那是人工评审的事。
- **不测 UI**。本 spec 不含前端组件测试，布局原型已用静态方式验证过结构决策。

### 现有的接缝

**没有。这是第一个 spec，代码库此刻不含任何应用代码。**

所以这不是"选一个已有接缝"，而是"在最高点开第一个接缝"。
Orchestrator 的 `run()` 之所以是最高的，是因为它包含了全部循环逻辑，
而它下面的东西（沙箱、模型）都是可以被替换的外部依赖。

- **GitHub 集成**
- **自定义域名**

### 实现时必须核对的官方约束

这些是硬约束，不是偏好。实现时逐条对照官方文档：

- **E2B SDK 必须用最新版**。旧版的 `connect()` 会覆盖 `autoPause` 导致沙箱被杀
  （E2B issue #875，2026-05-15 修复）
- **`connect()` 只延长沙箱寿命，不重置它**。要精确设置用 `setTimeout()`
- **沙箱创建时设置 `onTimeout: 'pause'`**，否则超时销毁而非暂停
- **`Sandbox.list()` 的过滤在服务端执行**。GC 依赖它，因此沙箱创建时
  必须打 `metadata: { workspace_id }`——不打的话 GC 找不到沙箱
- **暂停一个沙箱约 4 秒/GiB RAM**，且节点繁忙时返回 503，SDK 建议重试。
  批量场景下这个开销要纳入时序设计
