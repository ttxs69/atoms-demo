# 11 — 对话 + 预览界面布局

Type: prototype
Status: resolved
Blocked by: 10

## Question

依赖 ticket 10 的范围裁剪结论。用 `/prototype` 产出可比较的布局方案。

待定的决策：

- **整体骨架**：单栏（对话为主，预览弹出）/ 双栏（左对话右预览）/ 三栏？
- **移动端**：是否需要支持？
- **预览的位置**：内嵌 iframe 还是新标签页打开？
- **空状态**：新用户第一眼看到什么？
- **模式与角色的开关放在哪**
- 主题：亮/暗/跟随系统？
- **零状态的信任建立**：用户凭什么相信一个陌生网站能生成应用？

## Answer

Resolved 2026-09-12。

### 原型

`prototypes/ui-layout.html`（commit `097f555`）。纯静态，双击打开即可。

三个**结构性**差异的布局方案 + 四个状态，底部悬浮栏切换：

```
?v=a|b|c   &state=empty|generating|error|editing
```

- **A 对话主栏 + 抽屉预览**：对话始终占满宽度，预览滑入覆盖（`translateX`）。
  优点：阅读对话时视野最大。缺点：改应用时要来回切换。
- **B 双栏分屏**：左对话右预览并列。Atoms 的形态，但砍掉第三栏。
- **C 预览主栏**：应用是主角，对话退成 340px 侧栏。
  适合"已经在改一个能跑的应用"这个阶段。

### 决策

#### 整体骨架：B 双栏分屏，但带 A 的收起能力

**选 B 为主形态**，理由：

- ticket 10 的核心是**多轮迭代**（Q1 保留了多轮修改）。迭代的本质是
  "说一句 → 看结果 → 再说一句"，对话与预览必须**同时可见**，否则每轮都要切换
- C 的预览优先在"首次生成"阶段过早——那时用户最需要看的是"它在干什么"，不是空白画布
- A 的弊端在多轮修改时最明显：抽屉遮盖对话，用户看不到自己刚说的话

但要吸收 A 的一个优点：**预览可收起**。在首次生成的前半段（理解和计划），
对话是唯一有信息量的东西，此时预览是空白的。所以默认在"生成中"早期收起预览，
首个文件写入后再展开。这个时序与 ticket 09 的骨架先行正好对齐。

#### 移动端：对话优先，预览用全屏覆盖

三个方案在窄屏下都退化为**对话单栏**，预览通过顶部按钮全屏覆盖。
理由：ticket 10 已确认终点是"陌生人公开访问"，首次接触很大比例在手机上；
但移动端做"边聊边看预览"在物理上不可能。分阶段是唯一可行的做法
——手机上主要用来**发起**和**查看**，不指望做精细迭代。

#### 预览位置：内嵌 iframe，但保留新标签页出口

E2B 的 `getHost(3000)` 返回一个普通 HTTPS URL，作为跨域 iframe 嵌入没有特殊要求。

**已验证（2026-09-12）**：`*.e2b.app` 预览 URL 响应头为 `access-control-allow-origin: *`，
无 `X-Frame-Options`，无 CSP `frame-ancestors`。跨域 iframe 嵌入没有障碍。
PR #559（`fix-x-frame-to-prevent-clickjacking`）改的是 E2B 自己的控制台（`apps/web/next.config.mjs`），
与沙箱预览 URL 无关。**B 方案的前提成立，实现时无需回退。**

#### 空状态：三个样例 + 零配额门槛文案

原型里的空状态是三个可点击的样例（记录心情 / 待办清单 / CSV 变图表），
每个带一句"这能做什么"的副标题。

关于信任建立：**少说多做**。不放"AI 驱动的革命性平台"这类话，
只放两件事——

1. **三个具体样例**（用户看到能做什么，而不是被许诺什么）
2. **一句"不需要写代码，也不需要注册"**

第二句是关键：ticket 07 已定匿名认证，用户确实不需要注册就能试。
把这句话放在输入框上方，是**把已实现的事实当作信任锚**——
比任何营销文案都有说服力。二维码式的"我们很厉害"是多余的。

#### 角色开关：不暴露，只显示谁在说话

`@` 提及功能**不放进 MVP 的默认界面**。理由：ticket 10 只上了 3 个角色，
用户 `@` 的收益有限；而 ticket 06 已定 supervisor 会自动分派。
界面只需显示**谁在说话**（头像 + 名字 + 角色标签），不需要暴露选择器。

有一个例外：迭代阶段在输入框显示 `@ Alex` 这个 chip，
因为它暗示"你正在和工程师对话"，是拟人化的低成本体现。

#### 主题：跟随系统，亮色为主

实现成本低（CSS 变量 + `prefers-color-scheme`），但**暗色不做精细打磨**。
理由：预览区是 iframe，里面的应用有自己的主题，两套主题叠加容易出视觉冲突。
MVP 阶段统一亮色，暗色推到下一轮。

#### 状态可见性：三层

从原型的 `generating` 状态总结出三处状态显示，各有分工：

| 位置 | 内容 | 更新频率 |
|---|---|---|
| 顶栏 pill | 全局状态（生成中 / 运行中 / 需要确认） | 状态机迁移时 |
| 消息头部 pill | 当前动作（"正在写 src/App.tsx"） | 每个工具调用 |
| ACTIVITY 折叠区 | 完整事件日志 | 流式 |

第三层默认折叠——`docs/01` 记录 Atoms 把日志放在 Terminal 面板而非主视图，
非技术用户不需要看日志，但他们需要**知道日志存在**（可展开 = 可验证）。

### 原型暴露的三个约束

1. **对话栏宽度下限约 340px**。骨架先行的文件树要能显示 4 行不折行；
   安全门控失败卡片的代码块 + 两个按钮也在这个宽度内刚好排得下。
   这直接否掉了 C 方案更窄的侧栏设想。

2. **迭代状态在 B/C 下明显更好读**，因为预览始终可见。
   这是选 B 的主要依据——A 方案在 `editing` 状态下需要用户手动开抽屉。

3. **顶栏和消息头部的 pill 会重复**。原型里 `generating` 状态下
   顶栏显示"生成中"、消息头显示"正在写代码"，信息重叠但不冲突——
   前者是全局，后者是当前动作。实现时要注意不要合并成一个。

### 证据

- `prototypes/ui-layout.html` — 原型本体，三个方案可切换对比
- <https://docs.e2b.dev/network/public-url> — `getHost(port)` 返回普通 HTTPS URL
- curl 验证（2026-09-12）：`*.e2b.app` 响应头 `access-control-allow-origin: *`，无 `X-Frame-Options`，无 CSP `frame-ancestors`
- GitHub e2b-dev/E2B PR #559 — clickjacking 修复针对 `apps/web`（E2B 控制台），不影响沙箱 URL
- GitHub e2b-dev/E2B issue #539 — 用户在 iframe 里嵌入 E2B 沙箱的 Next.js 应用，E2B 团队确认嵌入本身可行
- `docs/01-atoms-core-features.md` — Atoms 的日志面板位置（Terminal 而非主视图）
